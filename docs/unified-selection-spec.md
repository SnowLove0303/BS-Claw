# BS Claw 选品模块统一正式需求与实现说明

> 本文是当前资料包的主规范。它把前期讨论的十类内容统一成一个可开发、可测试、可审计的业务契约。文中“计划/待核验”不是已实现能力。

## 一、十类统一内容与追溯编号

| 编号 | 内容 | 目标 | 主要产物 |
|---|---|---|---|
| SEL-01 | 用户目标与入口 | Codex/用户只表达业务目标 | 请求归一化契约、自然语言映射 |
| SEL-02 | 资源发现与预检 | 自动匹配端口、Profile、登录态、权限 | 资源快照、预检报告 |
| SEL-03 | 账号与会话 | 复用可用会话，阻止不满足条件的任务 | 会话能力、API-ready 判定 |
| SEL-04 | 候选获取 | 从慧策真实接口获取候选商品 | 候选快照、分页/限流契约 |
| SEL-05 | 条件筛选与排序 | 依据版本化规则自动决定候选集 | 条件版本、排序结果、决策证据 |
| SEL-06 | 选品动作执行 | 对选定候选执行真实业务动作 | 幂等写入、外部任务引用 |
| SEL-07 | 任务与状态 | 统一调度、进度、取消、超时、恢复 | 状态机、任务记录 |
| SEL-08 | 结果回查 | 确认真实业务结果而非接口成功 | 精确回查、结果摘要 |
| SEL-09 | 异常、审计与资源收口 | 保证失败可解释、租约一致、可恢复 | 脱敏审计、恢复队列 |
| SEL-10 | 验收、回归、发布与演进 | 形成独立可交付模块 | 四级审计、人工测试、回滚和版本策略 |

## 二、全自动阶段的明确含义

Phase 1 关闭业务人工确认：任务达到自动预检条件后，候选筛选和已允许的写入动作自动继续，不弹“是否提交”确认框。

这不允许以下行为：猜测账号密码、绕过登录/验证码/风控、忽略权限、跳过结果回查、在外部结果未知时重复写入。外部认证和安全条件是事实门禁，不是业务确认；不满足时任务自动阻断并保留恢复上下文。

## 三、端到端标准路径

```text
用户/Codex 业务请求
 -> 请求归一化与能力选择
 -> 选品 manifest/版本校验
 -> PortManager 源库查询
 -> 资源自动匹配/租约申请
 -> 端口、CDP、Profile、登录态、API-ready、权限预检
 -> 任务上下文与规则快照
 -> 候选 API 读取
 -> 条件筛选/排序/去重
 -> 自动执行 Action
 -> 外部任务轮询或业务对象精确回查
 -> 结果归一化与用户摘要
 -> 审计落库/租约释放/恢复状态收口
```

## 四、SEL-01 用户目标、入口与请求归一化

### 用户可表达的目标

用户可以表达“从某个已登录慧策资源获取符合条件的商品并执行选品动作”等业务目标。用户不需要提供 `moduleId`、`action`、`taskId`、`resourceId`、端口或 JSON。

### 系统归一化字段

```json
{
  "goal": "selection",
  "operation": "candidate-and-execute",
  "businessInputs": {},
  "resourceConstraint": {},
  "ruleVersion": "resolved-by-system",
  "requestedBy": "codex-or-user",
  "idempotencyKey": "generated-or-derived"
}
```

内部字段由系统绑定，不能让普通用户复制或填写。输入缺失时必须指出缺少的业务信息；不得用静态默认值伪造完整请求。

## 五、SEL-02 资源发现与预检

统一调度层调用 PortManager 的公开服务/适配器获取资源列表，至少需要可理解的名称、端口、启用状态、登录状态、更新时间和能力状态。用户不直接读数据库。

自动匹配顺序：明确业务约束 -> 已登录且 API-ready -> 端口和 Profile 可用 -> 并发策略允许 -> 最近状态新鲜。匹配失败时返回真实空状态和原因，不偷偷选择不符合条件的资源。

预检必须验证：资源存在、启用、端口监听、Chrome/CDP、Profile 未被占用、登录态、API-ready、慧策上下文、凭据引用有效、模块能力版本兼容和租约可申请。

## 六、SEL-03 账号与会话

默认复用已登记且满足条件的登录资源，不弹人工窗口。登录过期或没有可用资源时，进入 `AUTH_REQUIRED`/`RESOURCE_REQUIRED` 阻断；不得把“打开登录页”当成登录成功。

认证结果至少区分：页面可达、登录页面、已登录页面、API token 可用、业务接口可用。状态必须包含来源时间和新鲜度。

## 七、SEL-04 候选获取

候选读取必须封装在选品模块自己的 HTTP connector 中，负责请求构造、鉴权引用、超时、分页、限流、响应校验、脱敏和错误归一化。候选必须保存来源、读取时间、分页游标/外部任务引用和原始业务对象脱敏摘要。

## 八、SEL-05 条件、排序与决策

条件是版本化资料，不允许隐式写死在脚本中。第一阶段先提供规则契约：输入字段、比较方式、优先级、缺失字段处理、去重键、排序稳定性、上限和空结果策略。

规则不完整时必须阻断或以明确的“只读候选模式”返回，不能把临时样例当正式策略。每个候选都要保留命中/淘汰原因，供结果解释和审计回放。

## 九、SEL-06 动作执行

动作必须声明：读/写类型、资源选择模式、同资源互斥或跨资源并行策略、是否需要登录、超时、取消、恢复、幂等键和回查方法。

Phase 1 的自动写入前置门禁由系统完成，不做人工确认；门禁不通过则不写入。写入未知结果时先执行精确查询，不进行盲重试。供应商、店铺、商品和 SKU 标识必须从真实响应绑定，不能靠用户或开发者手抄。

## 十、SEL-07 任务、进度与状态

最小状态：

`RECEIVED -> NORMALIZED -> CAPABILITY_MATCHED -> RESOURCE_BOUND -> PREFLIGHT_PASSED -> CANDIDATES_READY -> FILTERED -> EXECUTING -> VERIFYING -> SUCCEEDED`

异常状态：`AUTH_REQUIRED`、`RESOURCE_BUSY`、`BLOCKED`、`FAILED`、`CANCELED`、`TIMED_OUT`、`RECOVERY_REQUIRED`。

每次状态变更记录阶段、时间、来源、可见消息、技术证据引用和下一步。长任务必须支持查询、取消、超时收口和恢复；状态不能停在“处理中”而无后续事实。

## 十一、SEL-08 结果回查

成功必须同时满足：外部动作返回可接受结果、业务对象/任务精确回查成功、资源/任务/审计状态一致、租约释放。HTTP 200、页面打开、任务入队和 JSON 可解析都不是最终成功。

结果至少包含：业务动作、成功/失败数量、对象摘要、外部任务引用、回查时间、失败原因、可恢复建议和下一步。禁止输出凭据、Cookie、Token、完整授权头或 Profile 路径。

## 十二、SEL-09 异常、审计与资源收口

所有异常都必须分类为用户输入缺失、资源门禁、认证门禁、外部 API、业务规则、并发冲突、超时取消、结果不确定或系统错误。每类都要定义是否可重试、重试前回查、租约处理和用户消息。

无论成功或失败都执行 finally 式资源收口：释放租约、停止临时 watcher、落审计、保留可重建运行数据；不可再生资源定义、schema、迁移、凭据引用和业务记录不得被清理。

## 十三、SEL-10 验收、回归、发布与演进

必须分别完成开发自检、一级架构审计、二级交互审计、三级真实路径审计、四级终审。交付前还要有用户可执行的人工测试文档；技术命令只能放在取证附录。

选品模块独立发布、独立回滚、独立版本；接入调度层仅通过 manifest/adapter/公开契约。任何 API、schema、规则版本变更必须登记变更单并回归 PortManager、BSClaw-Local、HuiceLoginAgent 共享路径。
